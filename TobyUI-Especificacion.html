1. Objetivo

Toby UI es un lenguaje declarativo propio para describir interfaces gráficas en Rocky OS (kernel x86_64 bare-metal en Rust). Describe qué debe aparecer y cómo organizarse, nunca cómo ejecutar lógica.

El runtime interpretará documentos .toby, calculará layout, aplicará tema, dibujará sobre framebuffer VESA y gestionará eventos/acciones registradas sin ejecutar código arbitrario.

2. Principios fundamentales

  • Declarativo: solo estructura, propiedades, distribución, recursos y referencias a acciones.
  • Separación: estructura (documento) ≠ apariencia (tema) ≠ presentación (renderer) ≠ comportamiento (eventos/acciones).
  • Tipado: todas las propiedades validadas por tipo (int, bool, string, enum).
  • Seguro: sin eval, bucles, condicionales generales, funciones, scripts ni acceso libre a sistema.
  • Determinista: layout reproducible con mismos datos.
  • Minimalista: basado en lo realmente usado (coincide con kit AQUA).
  • Bare-metal friendly: no_std + alloc, sin dependencias pesadas.

3. Diferenciación: TobyUI (runtime) vs Toby UI (lenguaje)

ConceptoUbicaciónDescripción
TobyUI (runtime)kernel/src/gui.rs, wm.rs, term.rs, cursor.rsEscritorio gráfico ya existente. Ventanas, foco, z-order, barra de tareas, menú inicio, terminal embebido, composición.
Toby UI (lenguaje)kernel/src/toby_ui/ (nuevo)Lenguaje declarativo para describir interfaces reutilizables. Parser, modelo tipado, layout, tema, renderer, eventos, acciones.

4. Estructura de módulos

Se creará el directorio kernel/src/toby_ui/ con los siguientes archivos:

kernel/src/toby_ui/
├── mod.rs
├── parser.rs      // Léxico + sintáctico + análisis
├── document.rs    // Modelo de documento validado
├── component.rs   // Componentes, defs y tabla
├── layout.rs       // Motor de layout propio
├── theme.rs        // Temas + nine-slice
├── resource.rs     // Carga PNG/BMP + validación rutas
├── renderer.rs     // Trait Renderer + CanvasRenderer
├── event.rs        // Eventos, foco, estados
├── action.rs       // ActionRegistry seguro

En kernel/src/main.rs se añadirá:

mod toby_ui;

5. Gramática conceptual

Formato XML-like minimalista, sin namespaces, sin atributos dinámicos.

5.1 Documento mínimo

<toby-app name="settings">
  <window title="Configuración" width="640" height="420">
    <column spacing="12" padding="20">
      <box id="account" title="Cuenta">
        <button id="profile" title="Editar perfil"/>
        <box id="privacy" title="Privacidad">
          <button id="permissions" title="Permisos"/>
        </box>
      </box>
      <button id="save" title="Guardar" action="settings.save"/>
    </column>
  </window>
</toby-app>

5.2 Reglas sintácticas

  • Raíz obligatoria: <toby-app>
  • Elementos autocerrados o con hijos según componente
  • Atributos key="valor" (comillas dobles)
  • Valores numéricos enteros (px implícitos)
  • Valores booleanos true/false
  • Identificadores id y claves action con formato [a-zA-Z][a-zA-Z0-9_.-]*
  • Sin comentarios XML arbitrarios o se limitarán
  • UTF-8

8. Layout Engine (propio, determinista)

Motor propio, sin flexbox completo. Calcula Rect(x,y,w,h) absoluto por nodo.

8.1 Unidades

  • Enteros en píxeles (px). No em, rem, %, vw/vh.
  • spacing, padding, margin, gap en px.

8.2 Tamaños

  • fixed: width/height explícitos
  • auto: se ajusta al contenido
  • fill: ocupa espacio restante disponible
  • proporcionales (limitados) si se definieran más adelante

8.3 Alineación

  • start, center, end, stretch
  • Aplica a eje cruzado/principal según row/column

8.4 Reglas

  • Padding/margin respetados
  • Spacing entre hijos
  • Contenedores anidados
  • Recorte implícito cuando convenga
  • Recalculable ante cambio de tamaño de ventana
  • Determinista (mismo árbol → mismo layout)

8.5 API conceptual

pub struct Rect { pub x:i32,y:i32,w:u32,h:u32 }
pub trait Layout {
  fn compute(node:&ValidatedNode, constraints:&Constraints) -> ComputedLayout;
}

9. Tema y nine-slice

El tema separa apariencia de estructura. Permite reutilizar componentes con distintos temas.

9.1 Elementos del tema

  • Imágenes PNG por estado (normal/hover/pressed/focused/selected/disabled)
  • Métricas (alturas, radios, caps, offsets)
  • Tipografías (inicialmente bitmap 8x8; extensible)
  • Colores (texto, fondo, bordes)
  • Bordes/esquinas
  • Padding interno
  • Sombra (trío RGB como en AQUA)

9.2 Estados visuales

EstadoUso
normalEstado por defecto
hoverRatón sobre componente
pressedPulsado/activo
focusedEnfocado (teclado)
selectedSeleccionado (radio/check/segmented/list)
disabledDeshabilitado

9.3 Nine-slice

Soporta slicing 3-part (ideal para piezas AQUA): left, body, right. También permite 9-slice completo. Las piezas se escalan solo el cuerpo, conservando proporción/extremos. Permite reutilizar left_button_*.png, segmented_*_*.png, graybar_*.png.

struct NineSlice { left: Rect, body: Rect, right: Rect, image: ResourceId }

10. Recursos (PNG/BMP)

  • Carga vía fs.rs existente (runtime desde disco)
  • Ruta autorizada únicamente (sin .., sin acceso fuera de directorio de recursos)
  • Cache mínimo por ResourceId
  • Decodificación con librería png interna (kernel/src/libraries/png) + inflate
  • Soporte BMP para cursor/recursos puntuales
  • Validación de integridad mínima
  • Ruta sugerida: /usr/share/tobyui/themes/default/ en rockydisk.img
pub struct ResourceRef { pub id: String, pub src: String }
pub enum ResourceKind { Png, Bmp }

11. Renderer (trait + implementación)

11.1 Trait Renderer

Abstrae presentación. Layout calcula posiciones; renderer dibuja.

pub trait Renderer {
  fn clear(&mut self, color: u32);
  fn draw_rect(&mut self, x:i32,y:i32,w:u32,h:u32, style: &RectStyle);
  fn draw_nineslice(&mut self, x:i32,y:i32,w:u32,h:u32, ns:&NineSliceRef, state: State);
  fn draw_image(&mut self, x:i32,y:i32, img:&ImageRef, src: &Rect, tint: Option<u32>);
  fn draw_text(&mut self, x:i32,y:i32, text:&str, font:&FontRef, color:u32);
  fn push_clip(&mut self, rect: Rect);
  fn pop_clip(&mut self);
  fn present(&mut self);
}

11.2 CanvasRenderer

Implementación inicial sobre gfx::Canvas:

  • Usa pixel, fill, rect, line, hline/vline
  • text8x8/char8x8 para texto inicial
  • dibujar_imagen, blit, blit_alpha
  • Respeta clip
  • Dibuja nine-slice descomponiendo en left/body/right
pub struct CanvasRenderer<'a> { canvas: &'a mut gfx::Canvas }
Preparado para conectar con Kira en futuro, sin acoplar al runtime TobyUI.

12. Sistema de eventos, foco y estados

12.1 Eventos crudos → eventos Toby UI

Se convierten input::poll() y mouse::poll()+mouse::tomar() (igual que gui.rs) a eventos jerárquicos.

12.2 Tipos de evento

  • MouseDown { x,y,button }, MouseUp { x,y,button }, MouseMove { x,y,dx,dy }
  • Click { x,y,button }
  • KeyDown { scancode,keycode }, KeyUp { ... }, Char { ch }
  • FocusGain, FocusLoss
  • HoverEnter, HoverLeave

12.3 Foco

  • Cadena de foco jerárquica (focus chain)
  • Solo componentes enfocables reciben foco
  • Navegación por teclado lógica
  • Un solo componente enfocado a la vez

12.4 Estados derivados

Estado efectivo = (enabled, hovered, pressed, focused, selected, disabled) → determina skin/imagen del tema.

12.5 Enrutamiento

  • Hit-test por posición tras layout (point_in_rect)
  • Prioridad al nodo más profundo bajo cursor
  • Eventos suben/bajan según necesidad
  • Click generado tras MouseDown+MouseUp sobre mismo nodo

13. Action Registry (seguro)

13.1 Principio

action="settings.save" es únicamente una referencia a un handler registrado. El documento nunca define funciones.

13.2 Estructura

pub type ActionHandler = fn(ctx: &ActionCtx) -> ActionResult;

pub struct ActionCtx {
  pub app_name: &str,
  pub node_id: Option<&str>,
  pub extra: &[(&str,&str)],
}

pub enum ActionResult { Ok, Err(&'static str) }

pub struct ActionRegistry {
  map: BTreeMap<String, ActionHandler>, // sin HashMap dinámico excesivo
}

13.3 Reglas

  • Solo se pueden registrar handlers existentes en runtime
  • Resolución por clave exacta (settings.save)
  • Si action no existe → error controlado en validación o ejecución
  • Invocación explícita tras validación
  • Sin ejecución desde parser
  • Registro externo (proceso/runtime de Rocky)

15. Integración con Rocky

15.1 Inspección realizada

  • gfx.rs + pantalla.rs: framebuffer VESA, Canvas, primitivas
  • input.rs + mouse.rs + ps2.rs: entrada por sondeo
  • gui.rs + wm.rs: TobyUI runtime (separado, NO se reemplaza)
  • fs.rs + disk.rs: lectura disco runtime
  • png + inflate: decodificación PNG
  • heap.rs + alloc: heap kernel
  • main.rs + shell.rs: arranque/bucle

15.2 Conexión con entrada

Reutilizar exactamente: input::poll(), mouse::poll(), mouse::tomar(). Convertir a eventos Toby UI.

15.3 Conexión con dibujo

Obtener Canvas vía pantalla::obtener_canvas()/pantalla::tomar_canvas(). Crear CanvasRenderer que envuelva dicho canvas.

15.4 Recursos

PNG del kit AQUA se copiarán a ruta autorizada en rockydisk.img (p.ej. /usr/share/tobyui/themes/default/). resource.rs los leerá vía fs.rs.

15.5 Ubicación

  • Código: kernel/src/toby_ui/
  • Compila con kernel: no_std + alloc, x86_64-unknown-none
  • No toca arranque/PMM/GDT/paginación/scheduler/syscalls
  • Complementario a wm/gui, no sustituto

16. Prohibiciones estrictas

  • Variables generales ni asignaciones arbitrarias
  • Funciones definidas por el usuario
  • Bucles ni recursividad programable
  • Condicionales de propósito general
  • Evaluación dinámica de expresiones
  • Intérprete de JavaScript
  • Ejecución de scripts
  • Acceso directo a memoria
  • Llamadas al sistema libres
  • Carga de bibliotecas arbitrarias
  • Ejecución de comandos del sistema
  • Acceso a archivos fuera de rutas autorizadas

Permitido: estados visuales, variantes declarativas, referencias action tipadas y validadas.

17.1 Estado real (fases 2-8)

Módulos ya presentes en kernel/src/toby_ui/: mod.rs, component.rs, document.rs, parser.rs, validation.rs, layout.rs, theme.rs, resource.rs, renderer.rs, event.rs, action.rs, app.rs, demo.rs y el documento demo.toby.

validation.rsComponente conocido, propiedad permitida, tipo correcto, enums de lista cerrada, obligatorias, id únicos, jerarquía (≥1 window; las hojas no admiten hijos).

event.rsTraduce la entrada cruda a eventos normalizados (Entrada::mover/botones_nuevos/tecla, puros; sondear() es lo único que toca mouse.rs/input.rs). Mantiene hover, pulsado y foco (Interaccion), resuelve la diana subiendo por los padres, genera clic sólo si abajo y arriba caen en el mismo nodo, y navega el foco con Tab saltando los deshabilitados. Traduce todo a Estado para el tema: deshabilitado > pulsado > hover > enfocado > normal. Las flechas no llegan: input.rs las descarta, así que Tab es la navegación disponible.
action.rsRegistro de acciones del runtime. El documento sólo nombra acciones (action="settings.save"); el código vive en el anfitrión como punteros a función fn(&mut C, &Peticion) -> Resultado registrados con Registro::registrar. despachar/despachar_nodo/despachar_click ejecutan la acción de un clic; una clave no registrada o mal formada devuelve ErrorAccion (error controlado), nunca ejecuta nada más. Claves con forma dominio.accion (1–3 segmentos [a-z_][a-z0-9_-]*, ≤64 bytes), comprobadas también al validar el documento mediante PropType::Accion y component::clave_valida. El BTreeMap interno da claves() en orden determinista.
app.rsEncadena todo: App::nueva/de_bytes/desde_fs (analizar + validar + disponer), procesar(Evento) (aplica el evento, conserva la Sesion entre fotogramas y despacha la acción del clic), atender_eventos/atender/sondear, pintar(&mut Canvas, font) y fotograma(...) = entrada + acciones + pintura. Paso resume cambios, acción y error sin perder nada. cambiar_tamano recalcula la disposición. Los fallos de montaje son ErrorApp (sintaxis / validación / recurso).
demo.rs + demo.tobyPrimera aplicación completa escrita en el lenguaje: una ventana con dos filas de botones (acciones reales + muestrario de variantes). El documento se incrusta con include_str!, así que la demo no depende del sistema de ficheros, y el mismo fichero se puede cargar de /usr/share/tobyui/demo.toby. El «código» son tres manejadores (settings.save, settings.reset, window.close) y el estado que tocan.

Verificación usada: andamio de pruebas en el host (%TEMP%\opencode\toby_pruebas) que incluye los mismos archivos del kernel mediante #[path], más un lienzo espejo de gfx::Canvas. 89 pruebas, 0 fallos: 74 unitarias (parser, validación, layout, tema, renderer, eventos, acciones, app y demo) y 15 de píxeles reales — 7 del renderer y 8 de punta a punta sobre el demo.toby de verdad (colores de cada variante, hover/pulsado/foco/sombra, anillo de foco, clic que ejecuta la acción, botón deshabilitado que no recibe nada, recorte al encoger la ventana, acción inexistente → error controlado y documento inválido → no monta). El kernel compila con cargo check --release --target x86_64-unknown-none y la imagen completa se genera con build.ps1.

Lo único que falta para verlo en pantalla: que el escritorio (gui.rs/wm.rs) llame a App::atender/pintar con el búfer de una ventana o con la pantalla completa. App::pintar ya acepta cualquier gfx::Canvas y app.rs documenta el bucle exacto con APIs existentes (wm::ventana, gfx::Canvas::from_buffer, wm::marcar_ventana).

18. Criterios de aceptación

  • Parser rechaza sintaxis inválida, componentes/props desconocidos
  • Validación aplica tipos, jerarquía, IDs únicos, límites
  • Layout reproducible con mismo árbol
  • Recursos solo desde rutas autorizadas
  • action desconocida → error controlado
  • Sin eval, bucles, funciones, scripts en .toby
  • Compila x86_64-unknown-none, no_std, alloc
  • No rompe wm/gui/shell/fs/entrada
  • Usa APIs existentes cuando posible
  • Separación clara TobyUI runtime vs Toby UI lenguaje
  • Nine-slice funciona con piezas AQUA
